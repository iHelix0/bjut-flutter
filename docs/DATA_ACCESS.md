# 数据访问与安全边界

记录日期：2026-09-01

状态：候选政策；项目负责人已声明拥有授权，具体范围仍需记录

## 基本判断

项目负责人已明确说明本项目拥有相应授权。本文件不再把“是否有授权”作为项目阻塞项，但仍要把授权的主体、系统、接口、账号类型、可执行操作和有效期记录清楚，避免实现超出授权范围。

因此，每个数据源进入实现前都要回答：

- 数据由谁提供，接口或页面面向谁开放；
- 是否存在正式 API、使用说明、许可或校内联系人确认，以及授权是否允许反向代理；
- 是否包含个人信息、敏感个人信息或他人信息；
- 客户端需要保存什么，保存多久，用户如何清除；
- 请求频率和失败重试是否会给校内系统造成额外负担；
- 接口变化、权限撤回或账号退出时如何失效。

## 数据源优先级

1. 正式提供并明确允许使用的 API 或数据文件；
2. 学校官网公开页面和公开数据；
3. 经明确许可、由用户本人账号读取的只读接口；
4. 已获授权但尚无正式文档、仅通过分析官方客户端发现的接口。

第四类可以在授权范围内作为研究对象，但必须先用脱敏样本确认字段和行为；不能绕过安全机制，也不能把推断当成接口稳定性保证。

## 数据分级候选

| 级别 | 示例 | MVP 处理 |
|---|---|---|
| 公开 | 官网通知、公开校历、地点与开放时间 | 可优先验证，仍需遵守来源与频率要求 |
| 本人一般信息 | 本人课表、本人通知 | 获得接口和认证许可后，只读、最小缓存 |
| 敏感或高风险 | 身份证件、财务、位置、人脸、门禁、健康数据 | MVP 排除 |
| 他人信息 | 通讯录、成绩名单、审批内容 | MVP 排除，除非未来有明确业务与正式授权 |

校园卡余额属于本人财务相关信息，仍按最小化展示和最小缓存处理。充值属于交易写操作，必须有单独的订单、支付和回执设计。

## 凭据与日志

- 项目不接收或保存用户密码、Cookie、令牌、短信验证码和人脸数据。
- 真机登录由项目负责人亲自操作；调试材料在分享前移除请求头、查询参数中的令牌以及个人字段。
- 默认只记录请求类别、耗时、状态分类和匿名错误标识，不记录完整 URL 参数、请求体或响应体。
- fixture 使用伪造姓名、学号、课程和标识符，并保留字段结构而非真实值。
- 如果采用反向代理，代理只接收完成业务所需的最小字段，并承担令牌隔离、限流、审计和错误脱敏；代理本身不应成为“为了能调接口”而无限扩大的后端。

## 需要校内确认的事项

- 已获授权的书面或可核验范围，尤其是充值和代理是否包含在内；
- 是否存在可用的开放接口、测试环境和测试账号；
- 允许的认证方式、令牌生命周期和退出机制；
- 允许缓存的数据字段、时长和设备安全要求；
- 请求频率、客户端标识、问题联系人和接口停用流程；
- 充值支付渠道、订单回调、退款/冲正和对账方式。
